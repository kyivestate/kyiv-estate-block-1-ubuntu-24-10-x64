# Документація блоків Kyiv Estate

Ця папка описує production-контури платформи станом на 30 липня 2026 року. Документи відображають фактичні файли, таблиці, служби й межі доступу. Секрети, паролі, приватні SSH-ключі та service-account JSON навмисно не включені.

| Блок | Документ | Відповідальність |
|---|---|---|
| Блок 1 | `BLOCK_1_RESIDENTIAL_UA.md` | Квартири й будинки Києва: OLX/Rieltor → PostgreSQL → Google Sheets. |
| Блок 1.2 | `BLOCK_1_2_COMMERCIAL_UA.md` | Комерційна нерухомість Києва: окремі парсери, таблиці та Google Sheets. |
| Блок 2 | `BLOCK_2_WINDOWS_TELEGRAPH_UA.md` | Ізольований Windows/Telegraph-контур: читання даних і безпечне повернення URL. |

## Глобальні правила

1. PostgreSQL є джерелом істини; Google Sheets є контрольованим представленням даних.
2. Кожний запис ідентифікується парою `source + external_id`. Для OLX `external_id` має формат `olx_ID…`; для Rieltor — `rieltor_…` із номером у URL.
3. Парсери, AI-обробка, status-check і Sheets-синхронізація працюють лише на Mac у production-контурі.
4. Windows не отримує адміністраторських ключів Google, PostgreSQL чи Mac. Він взаємодіє лише через обмежений SSH-тунель і ролі Блоку 2.
5. Не можна використовувати `clear()`, масове видалення рядків або ручний перезапис production-таблиць для «виправлення» даних.

## Спільні інфраструктурні компоненти

- macOS LaunchAgents планують виконання.
- PostgreSQL `real_estate` зберігає житлові, комерційні й staging-дані Блоку 2.
- `SheetsLock` гарантує, що два процеси не пишуть у Google Sheets одночасно.
- `process_lock` і каталогові lock-файли не допускають паралельні дублікати parser/backfill-задач.
- `backups/production/` містить зашифровані правами ОС дампи БД, експорти Sheets і контрольні суми.

## Порядок роботи з документацією

Перед зміною production-процесу спочатку визначте блок, прочитайте його документ повністю, перевірте залежні LaunchAgent-и та використайте health/audit-скрипти саме відповідного блоку. Зміни меж одного блоку не повинні змінювати дані або планувальники іншого.
